# 06 — The pipeline: from an upload to the knowledge core

This document covers the five files under `backend/pipeline/`:

- `backend/pipeline/ingestion.py` — storing uploads, downloading YouTube audio
- `backend/pipeline/extraction.py` — reading PDF, PPTX, DOCX and plain text, routing audio to transcription
- `backend/pipeline/media.py` — ffmpeg normalisation and the `Transcriber`
- `backend/pipeline/cleaning.py` — two cleaners, one for documents and one for speech
- `backend/pipeline/knowledge.py` — the `KnowledgeCore` model and the `KnowledgeExtractor`

It also reaches into a handful of files just outside the package where a decision in
the pipeline is actually enforced — mainly `backend/handlers/ingest_handler.py`,
`backend/api/schemas.py` and `backend/llm/openrouter.py` — because you cannot explain
some of these lines honestly without them.

---

## The shape of one upload, before the detail

A user drops a lecture recording on the canvas. The browser posts it to
`POST /api/projects/{id}/upload`, which streams it to a temporary file on disk rather
than reading it into memory, writes an `ingest` job row whose `source_ref` is the path
of that temporary file, and returns immediately. A worker picks the row up and calls
`IngestHandler.run`.

From there the five files run in order.

`ingestion.py` puts a durable copy of the file into the file store under
`{project_id}/sources/{uuid}{suffix}`, so that the original survives after the
temporary upload is deleted. If the source was a YouTube link instead of a file, this
is where the URL is authorised — the host has to be YouTube and it has to resolve to a
public address — and then yt-dlp downloads the audio track into a scratch directory and
that gets stored instead.

`extraction.py` looks at the file's extension and decides who should read it. A `.pdf`,
`.pptx` or `.docx` goes to `DocumentReader`, which runs the appropriate parser in a
worker thread and returns the text. A `.wav`, `.mp4` and so on goes to the
`Transcriber`.

`media.py` is that `Transcriber`. It shells out to ffmpeg, in a worker thread, to
convert whatever the user uploaded into 16 kHz mono PCM WAV, then hands that file to
the LLM provider's `transcribe` method. The provider — OpenRouter, running
`google/gemini-2.5-flash` — base64-encodes the WAV and sends it as an `input_audio`
content part. Words come back.

`cleaning.py` takes those words and cleans them with the rules the source can survive,
and which rules those are depends on where the text came from.

Speech goes through `clean_transcript`, which is two passes. First a set of regular
expressions strips timestamps, speaker labels, bracketed asides and filler words.
Then the text is cut into 4,000-character chunks and every chunk is sent to the model
concurrently with a prompt whose entire job is to repair grammar and punctuation
*without* changing meaning. What comes back is joined into clean prose.

A document — a PDF, a slide deck, a Word file, a plain text file — goes through
`clean` instead, which does neither of those things. It normalises whitespace, removes
characters that carry no text, and stops. Those transcript rules delete every
parenthesised and bracketed span, and on a maths or computer-science PDF that is `f(x)`,
`[0,1]`, `O(n log n)` and every bracketed citation gone. They used to run on everything.
The split is section 4 of this document and it is one of the better things to be able
to talk about, because the failure was silent.

`knowledge.py` takes that prose and asks the model for one structured document: the
`KnowledgeCore`. Title, summary, concepts, a section hierarchy, notes, definitions,
examples and key facts. If the text is long it is chunked, extracted concurrently, and
the partial cores are merged with per-collection de-duplication.

`IngestHandler` then validates the core, and commits two artifacts: the source file and
the core. Every study artifact the user later generates — quiz, flashcards, slides,
mock exam, study guide, cheat sheet, mind map — is generated by serialising *that core*
to JSON and passing it as context. Not the transcript. That is the central design claim
of the project, and the last section of this document is about defending it.

One verified fact you can state plainly: this whole audio path was tested end to end.
A real WAV was generated with macOS `say`, pushed through ffmpeg normalisation, through
OpenRouter transcription, and into a knowledge core. 58 words came back transcribed.
It is not a hypothetical path.

## The error type

```python
class IngestionError(RuntimeError):
    """A source could not be fetched or stored."""
```

`ingestion.py:26-27`. Each pipeline stage defines its own exception class:
`IngestionError` here, `ExtractionError` in extraction, `MediaError` in media. The
value of this is not clever error handling — it is that when a job fails, the message
that reaches the user through the job row carries the name of the stage that failed.
`IngestionError` means "we never got the file". `ExtractionError` means "we got it and
could not read it". Those are different problems for the user.

```python
class UnsafeSourceError(IngestionError):
    """
    A source URL was refused before anything was fetched.

    Separate from its parent so a refusal reads as a decision rather than a
    download that went wrong, and permanent for the same reason both are:
    `is_transient` in the job runner classifies by exception type and by the
    words in the message, and neither this class nor the messages it carries
    look like a busy upstream. A refused job therefore fails once instead of
    replaying the same request until the attempt limit.
    """
```

`ingestion.py:30-40`. A second error type, and a subclass rather than a sibling, which
is the decision worth explaining.

It inherits from `IngestionError`, so `store_youtube`'s own `except IngestionError:
raise` at line 201 lets it through untouched and every existing caller that catches
`IngestionError` still catches it. Nothing above this file had to learn a new name.

The reason it is a distinct class at all is the message the user reads. "Could not
download `<url>`" is what a failed fetch says, and it is wrong here: nothing was
fetched, and nothing was going to be. A refusal is a decision, and it should read like
one — `'169.254.169.254' is not a YouTube host` tells the user what to change.

The classification note in the docstring is the part to have ready. `is_transient` in
`backend/services/job_runner.py` decides whether a failed job goes back on the queue. It
tests the exception type against `TRANSIENT_EXCEPTIONS`, and failing that, looks for
transient-sounding phrases and labelled HTTP status codes in the message. `UnsafeSourceError`
is in neither set, and its messages contain no status code and no phrase like "timed out",
so a refused fetch fails once. That matters more than it sounds: an SSRF attempt that
was requeued would be three attempts at the same internal address rather than one, which
is both pointless and noisier in the logs. `backend/tests/test_api.py:837` asserts it
directly.

## `StoredSource`

```python
@dataclass(frozen=True)
class StoredSource:
    """Where a source ended up and what it was called."""

    key: str
    original_name: str
    source_type: str
    size_bytes: int
```

`ingestion.py:43-50`. A small immutable record. `key` is the storage key inside the
file store, not a filesystem path — that distinction matters, because the store is free
to be a directory today and object storage tomorrow, and nothing outside the store
should be constructing paths. `original_name` is what the user called it, kept
separately because the stored key is a UUID and would otherwise be meaningless in the
UI. `size_bytes` is read back from the store after writing rather than trusted from
the upload, which means it is the size of what actually landed.

`frozen=True` is deliberate: this is a fact about something that has already happened.
Nothing should be mutating it. Contrast with `Extracted` in `extraction.py`, which is a
plain mutable dataclass because the extraction service genuinely does add to its
metadata after construction.

`ingestion.py:158-167`. This constructor pattern — `Optional` dependency, default to the
shared singleton — repeats in every class in this package: `ExtractionService`,
`Transcriber`, `TextCleaner`, `KnowledgeExtractor`. The reason is testing. Every one of
these can be constructed with a stub in a unit test with no monkeypatching and no

way.

The `guard` parameter is the second use of the same pattern and it pays for itself
immediately. `YouTubeUrlGuard` resolves hostnames through DNS, and a test suite that
did that would be slow, flaky and dependent on the machine's network. Injecting a
`StubResolver` that answers with fixed addresses — `backend/tests/test_api.py:737` —
lets the whole guard be tested with no network at all, including the case where a
genuine YouTube hostname resolves to an internal address, which you could not produce
against real DNS.

## `store_upload`

```python

        """File an already-downloaded upload under its project."""
        suffix = Path(original_name).suffix or Path(file_path).suffix

```

`ingestion.py:169-172`. The suffix is taken from the *user's* filename first and only
falls back to the staged temp file's suffix. That ordering is right round: the upload
endpoint does try to preserve the suffix when it creates the `NamedTemporaryFile`, but
the user's original filename is the more reliable statement of what the file is, and
the extension is what the whole of `extraction.py` routes on. Getting it wrong here
means a PDF gets read as plain text later.

The key is `{project_id}/sources/{uuid}{suffix}`. Project-scoped so that listing or
deleting a project's sources is a prefix operation, and UUID-named so two users
uploading `lecture.pdf` cannot collide and so nothing from the user's filename reaches
the filesystem. That second point matters: `FileStore.resolve` also refuses keys that
escape the store root, but not putting attacker-controlled text into a path in the
first place is the cheaper defence.

than ffmpeg, but it is the same class of problem, and it is the honest answer if an
interviewer asks whether every blocking call is covered.

### The two security holes, and the guard that now stands in front of them

This is the most substantial security work in the project and it happened in two stages,
because the first fix closed the smaller of two holes and the second closed the larger.

**The first hole: arbitrary local file read.** `source_type` is a caller-supplied string
on the ingest job payload, and `source_ref` is another. If a caller posted
`source_type: "youtube"` with `source_ref: "/etc/passwd"`, that path went straight into
`yt_dlp.extract_info`. yt-dlp does not only speak HTTP — given a bare filesystem path it
will happily open the local file, probe it, and treat it as media. A YouTube ingest was
therefore an arbitrary local file read, reachable by anyone who could create a job.

That one is closed in the request schema, at `backend/api/schemas.py:47-62`:

```python
    @model_validator(mode="after")
    def youtube_ref_is_a_url(self) -> "IngestRequest":
        """
        Keep the downloader on the network.

        Given a bare path yt-dlp will happily read a local file, which would turn
        a YouTube ingest into an arbitrary file read.

        This is a cheap early rejection, not the guard: it says nothing about
        where the URL points, and an http(s) URL naming an internal address is
        an SSRF. `YouTubeUrlGuard` in `backend/pipeline/ingestion.py` authorises
        the host, immediately before the call that fetches it.
        """
        if self.source_type == "youtube" and not self.source_ref.startswith(("http://", "https://")):
            raise ValueError("source_ref must be an http(s) URL for a youtube source")
        return self
```

What it accepts: any `source_ref` beginning `http://` or `https://`, when
`source_type` is `"youtube"`. What it rejects: everything else in that case —
absolute paths, relative paths, `file://`, `ftp://`, bare hostnames. It is a
`model_validator(mode="after")` rather than a `field_validator` because the rule is a
relationship between two fields; it needs `source_type` and `source_ref` at the same
time, and only a whole-model validator sees both.

It runs at `backend/api/routes/jobs.py:52-55`, where the job payload is parsed through
`REQUEST_MODELS[request.type]` before the job row is written. That placement is
important to be able to state: the request is rejected with a 400 and **no job row is
created at all**. Two tests pin this down, at `backend/tests/test_api.py:648` and
`:684` — one asserts the 400 and that the jobs table is still empty, the other asserts
a real YouTube URL still constructs, so the check is not just "reject everything".

Read the last paragraph of that docstring, because it is the honest label on what this
check is. It is a scheme check, not a host check. `https://169.254.169.254/latest/meta-data/`
passes it. That was the second hole.

**The second hole: full-response server-side request forgery.** `source_type: "youtube"`
only ever named the field. It did not constrain where the fetch went. Handed a URL its
extractors do not recognise, yt-dlp falls through to its **generic** extractor, which
fetches the URL and, when the response is not media, downloads the response body
verbatim. The pipeline then does what it does to any downloaded source: stores it,
extracts text from it, builds a knowledge core, and commits it as an artifact in the
caller's own project — which the caller can then open and read.

That is not a blind SSRF where you infer things from timing. It is a full-response one:
whatever the server could reach, the attacker got the body of, rendered as a readable
artifact. Cloud instance metadata, `localhost`, this API's own routes, anything else on
the network segment. It was proven end to end against a stand-in for a metadata
endpoint, and the artifact's summary contained the response body verbatim.

The fix is the two classes at `ingestion.py:53-155`, and the placement is the first
thing to say about it.

```python
class YouTubeUrlGuard:
    """
    Refuses any URL that is not a public YouTube address.

    `source_type: "youtube"` is a label the caller chose, not a constraint on
    where the fetch goes: yt-dlp hands an unrecognised URL to its generic
    extractor, which downloads whatever the far end returns, and the ingest
    pipeline then stores those bytes, extracts text from them and commits them
    as an artifact the caller can read back. Without this check the field is a
    full-response SSRF against anything the server can reach, so the guard sits
    here, immediately before the call that makes the request, rather than only
    at the HTTP door where one route already bypassed the request model once.
    ...
    """
```

`ingestion.py:69-87`. The guard lives next to the dangerous call, not at the API edge.
The previous version of this document said that defence in depth would put the check
immediately above `extract_info`, and this is that. The reason is in the last clause of
the docstring and it is not hypothetical: a route had already been found writing an
ingest payload by hand instead of through `IngestRequest`, so the schema validator never
ran for it. A check at the edge protects the doors you remember; a check here protects
the call.

`self._guard.check(url)` is the first statement in `store_youtube`, before the log line
and before `yt_dlp.YoutubeDL` is even constructed. `backend/tests/test_api.py:822`
asserts exactly that by monkeypatching `YoutubeDL` to raise if it is ever built, then
calling `store_youtube` with a metadata-service URL and asserting the `UnsafeSourceError`
comes out. The downloader never sees a refused URL.

#### The host check

```python
    ALLOWED_HOSTS = frozenset({"youtube.com", "youtu.be", "youtube-nocookie.com"})

    def _is_youtube(self, host: str) -> bool:
        return any(
            host == allowed or host.endswith(f".{allowed}") for allowed in self.ALLOWED_HOSTS
        )
```

`ingestion.py:89` and `ingestion.py:134-137`. An allowlist of three hosts, and a match
rule that is deliberately not the obvious one.

The obvious rule is `allowed in host` — a substring test. That accepts
`youtube.com.evil.tld`, because the allowed name really is a substring of it. It also
accepts `https://evil.tld/youtube.com`, if you test against the whole URL rather than
the host. Both are the classic way an allowlist gets bypassed.

The rule here is equality, or a suffix match against `"." + allowed`. So `youtube.com`
passes, `music.youtube.com` passes as a proper subdomain, and `youtube.com.evil.tld`
fails because it does not end in `.youtube.com`. The leading dot is the whole trick: it
is what makes this a subdomain test rather than a suffix test, and without it
`notyoutube.com` would pass. Four separate lookalikes are pinned at
`backend/tests/test_api.py:792`.

```python
    @staticmethod
    def _host(url: str) -> str:
        """The hostname to authorise, normalised so no spelling of it slips past."""
        parsed = urlparse(url)
        if parsed.scheme not in {"http", "https"}:
            raise UnsafeSourceError(
                f"A youtube source must be an http(s) URL, not '{parsed.scheme or url}'"
            )

        host = (parsed.hostname or "").strip().rstrip(".").lower()
        if not host:
            raise UnsafeSourceError("A youtube source URL must name a host")
        return host
```

`ingestion.py:120-132`. Getting the host out, and every operation on that one line is
closing a specific way of writing the same name differently.

`parsed.hostname` rather than `parsed.netloc`: `netloc` carries the userinfo and the
port, so `https://youtube.com@evil.tld/` has a `netloc` that starts with `youtube.com`
and a real host of `evil.tld`. `hostname` gives the actual host and nothing else.

`.rstrip(".")` removes the trailing dot of a fully-qualified domain name. `youtube.com.`
and `youtube.com` are the same host to DNS, and without this they are different strings
to the allowlist.

`.lower()` because DNS is case-insensitive and `YouTube.COM` is the same host.

The scheme check repeats what the request schema already said, which is the point of
defence in depth: this class does not assume the schema ran.

#### The address check

Passing the host check is not enough, and the reason is worth stating plainly: a name
you allow can still point somewhere you do not. Whoever controls DNS for a hostname
decides what it resolves to, and a hostname under an allowed suffix that resolves to
`127.0.0.1` would otherwise walk straight through.

```python
    NON_PUBLIC_RANGES = (
        "is_private",
        "is_loopback",
        "is_link_local",
        "is_multicast",
        "is_reserved",
        "is_unspecified",
    )

    def _is_public(self, address: IPAddress) -> bool:
        return not any(getattr(address, name) for name in self.NON_PUBLIC_RANGES)
```

`ingestion.py:91-98` and `ingestion.py:139-140`. Six properties, checked by name through
`getattr`, and the list is doing real work rather than being thorough for its own sake.
`is_private` covers RFC 1918 and its IPv6 equivalent. `is_loopback` covers `127.0.0.0/8`
and `::1`. `is_link_local` is the one that matters most in a cloud deployment, because
`169.254.169.254` — the instance metadata endpoint on AWS, GCP and Azure — is link-local,
and that address is the single most valuable thing an SSRF can reach.

Writing them as strings and reading them with `getattr` rather than as six `or`ed
attribute accesses means adding a category later is one line in a tuple, and the tuple
reads as a list of what "not public" means.

```python
        for text in self._resolver.addresses(host):
            address = self._address(text)
            if not self._is_public(address):
                raise UnsafeSourceError(
                    f"'{host}' resolves to {address}, which is not on the public internet."
                )
```

`ingestion.py:113-118`. **Every** answer is checked and **one** bad answer refuses the
whole URL. That is fail-closed rather than fail-open, and it is the right direction:
a resolver can legitimately return several addresses for one name, and an attacker who
controls the name can return a public address and an internal one together. If the check
were "does any answer look public" then that pair would pass and yt-dlp might connect to
either. `backend/tests/test_api.py:806` pins exactly that case with a real-looking public
address followed by `127.0.0.1`.

```python
class HostResolver:
    """Every address a hostname currently points at."""

    def addresses(self, host: str) -> List[str]:
        """The resolved addresses, refusing the host outright if it has none."""
        try:
            records = socket.getaddrinfo(host, None, proto=socket.IPPROTO_TCP)
        except socket.gaierror as error:
            raise UnsafeSourceError(f"The host '{host}' does not resolve: {error}") from error

        found = [str(record[4][0]) for record in records]
        if not found:
            raise UnsafeSourceError(f"The host '{host}' resolves to no address")
        return found
```

`ingestion.py:53-66`. Resolution is its own class for one reason: so it can be replaced
in a test. It is four lines of real work wrapped in a name, and that name is the seam.

`socket.getaddrinfo` rather than `socket.gethostbyname`, because the latter returns one
IPv4 address and nothing else. `getaddrinfo` returns every record, IPv4 and IPv6 both,
which is what a check that has to see all of them needs. `proto=socket.IPPROTO_TCP`
deduplicates the result — without it the same address comes back once per socket type.

`record[4][0]` is the first element of the `sockaddr` tuple, which is the address itself.
It is an ugly index, and it is what the standard library returns.

A name that does not resolve is refused rather than passed through. That is fail-closed
again: an unresolvable host cannot be checked, and something that cannot be checked
should not be fetched.

```python
    @staticmethod
    def _address(text: str) -> IPAddress:
        """
        A resolved answer as an address object, unwrapped and fail-closed.

        An IPv4-mapped IPv6 answer is checked as the IPv4 address it stands for,
        and an answer that will not parse at all is refused rather than allowed.
        """
        try:
            address: IPAddress = ipaddress.ip_address(text.split("%")[0])
        except ValueError as error:
            raise UnsafeSourceError(f"Could not read the resolved address '{text}'") from error

        return getattr(address, "ipv4_mapped", None) or address
```

`ingestion.py:142-155`. Three small things, each one a bypass that would otherwise work.

`text.split("%")[0]` strips the scope identifier from a link-local IPv6 address.
`getaddrinfo` returns `fe80::1%en0`, and `ipaddress.ip_address` raises on that string
rather than parsing it — so without the split, a link-local IPv6 answer would land in
the `except` branch. It is refused either way here, but only because the `except` branch
is fail-closed; stripping the scope means it is refused for the right reason, by the
`is_link_local` check.

`ipv4_mapped` is the interesting one. `::ffff:127.0.0.1` is a legal IPv6 address that
*means* `127.0.0.1`, and as an `IPv6Address` object it reports `is_loopback` — but not
every mapped internal address is caught that way, because an `IPv6Address` wrapping a
private IPv4 address does not report `is_private`. Unwrapping first means the six checks
run against the address that traffic will actually go to. `getattr(address, "ipv4_mapped", None)`
rather than a direct attribute access because `IPv4Address` has no such attribute at
all, and `or address` because `ipv4_mapped` is `None` for an ordinary IPv6 address.

`except ValueError: raise UnsafeSourceError` is the fail-closed default. Anything the
address parser cannot read is refused. The alternative — treat unparseable as fine —
is how these checks get bypassed.

#### The residual, and say it before they do

The check happens at **resolve time**, not at **connect time**. The guard resolves the
host, approves the answers, and then hands the URL — a string — to yt-dlp, which resolves
it again itself and connects. Two things fit in that gap.

A DNS rebind: a name whose TTL is zero can answer with a public address for the guard's
lookup and an internal one for yt-dlp's, seconds later. And a redirect: an allowed
YouTube host can return a 302 to an internal address, and yt-dlp will follow it, because
the guard never sees the second URL.

Closing that properly means the check and the connection have to use the same address.
In practice that is either a pinned-IP socket — resolve once, approve, and connect to
that exact address with the hostname carried in the `Host` header and the TLS SNI — or
routing the fetch through an egress proxy that enforces the policy at connect time.
Neither is a small change against a library that does its own networking, which is why
the current guard stops where it does. It closes the whole class of "point the field at
something else"; it does not close an attacker who also controls a DNS zone or a
redirect from an allowed host.

That is the honest boundary of the threat model, and volunteering it is worth more than
being asked for it.

# 2. `backend/pipeline/extraction.py`

174 lines. This file is where the "single responsibility" split is easiest to point at
on screen, because two classes with clearly different jobs sit in the same file, and a
third — `Transcriber` — is imported from `media.py`.

Before the split there was one class that decided what a file was, parsed PDFs,
unpacked PPTX, and also drove transcription. Now:

- `ExtractionService` **routes**. It looks at a suffix and decides who handles it. It
  owns no parser.
- `DocumentReader` **reads**. It owns every document parser and knows nothing about
  audio, storage or async.
- `Transcriber` (in `media.py`) **listens**. It owns ffmpeg and the provider call and
  knows nothing about documents.

The reason that matters in practice, and the reason to give if asked: adding a new
document format touches `DocumentReader` only; changing transcription providers touches
`media.py` only; and `ExtractionService` can be tested by injecting stubs for both
because of the constructor at line 131.

# 4. `backend/pipeline/cleaning.py`

177 lines. Two cleaners, and which one a source gets is the most important line in the
file.

## Why there are two cleaners

Start here, because it is the thing that changed and the reason it changed is a bug
worth telling.

The file used to have one public entry point, `clean`, and everything went through it:
a lecture recording, a PDF, a slide deck, a Word document, a plain text file. It applied
`TRANSCRIPT_NOISE` — four regular expressions — to all of them, and those four rules
delete every parenthesised span, every bracketed span, every run of two or more capital
letters followed by a colon, and every timestamp.

Those rules are exactly right for a transcript. `(laughs)`, `[inaudible]`, `[crosstalk]`,
`SPEAKER:` and `00:14:32` are noise the transcription produced and nobody said. In
speech, parentheses and brackets hold nothing a human uttered.

On a document they are a disaster. Run them over a mathematics or computer-science PDF
and `f(x)` becomes `f`, `[0,1]` disappears, `O(n log n)` becomes `O`, every bracketed
citation like `[Knuth 1998]` vanishes, `NOTE:` and `CPU:` are eaten by the capital-letters
rule, and the ratio `3:14` is eaten as a timestamp. Then the whitespace rule collapsed
every newline, which flattened the `--- Page N ---` and `--- Slide N ---` markers the
readers had just inserted into a single unbroken line.

Nothing raised. No exception, no warning, no failed job. The knowledge core was simply
built on mangled text, and every artifact under it was built on the core. That is the
same failure shape as the locale bug described below: plausible-looking output that is
quietly about the wrong document. This project has now been bitten by that shape twice,
which is the honest thing to say about it.

So the file was split. `clean(text)` is for documents and is conservative. It removes
characters that carry no text at all, normalises spacing, and stops — it cannot delete a
character the author typed. `clean_transcript(text)` is for speech and keeps the old
rules unchanged, because they were never wrong for speech.

`backend/tests/test_pipeline.py:217` asserts a document keeps `f(x) = 2x`, `[0,1]`,
`O(n log n)`, `[Knuth 1998]`, `NOTE:` and `3:14`; `:230` asserts a transcript still loses
`(laughs)`, `[inaudible]`, `SPEAKER:` and `12:34`. Both are needed: the fix has to close
the hole without closing the feature.

## Why the transcript path is two passes

Given the transcript path is the one that kept the regex-then-model shape, the older
question still applies to it: "why not just let the model do all of it?" The answer has
three parts.

Regular expressions are free, instant and deterministic. Stripping a timestamp or the
word "um" does not need a language model and does not benefit from one, and doing it
first means those tokens are never paid for.

More importantly, they reduce what the model is asked to do. If you hand the model a
transcript full of `00:14:32` and `SPEAKER 1:` and ask it to fix grammar, you are asking
it to make a judgement about whether those are content. Removing them first makes the
instruction unambiguous.

And the two passes fail differently, which is the point. A regex cannot invent text —
worst case it deletes something it should have kept. A model cannot be relied on not to
rewrite — worst case it summarises. Doing the destructive-but-bounded work with regexes
and the judgement work with a model puts each failure mode where it can be reasoned
about.

The model pass exists because regexes cannot fix what actually damages a transcript.
Speech-to-text output has no sentence boundaries in the right places, has homophone
errors, and spells a technical term four different ways across an hour. All of that
degrades the knowledge core. Only a model can repair it.

None of those three reasons applies to a typed document, which is why the document path
has no model pass at all. That is argued properly under `clean` below.

### The one-word locale bug

Note the spelling on line 23: **"Do NOT summarise"**. British.

When no `OPENROUTER_API_KEY` is set, `get_provider()` returns `OfflineProvider`
(`backend/llm/factory.py:19-28`) — a deterministic fallback that derives artifacts from
word-frequency analysis so that every pipeline stage still runs without a key. That
provider has to distinguish two kinds of prompt: prompts that want something *new*
derived from the input, and prompts that want the input *back*, edited. A cleaning pass
is the second kind. If the offline provider ran its frequency heuristic on a cleaning
prompt it would return a synthetic study document instead of the transcript.

The gate that makes that decision is `backend/llm/offline.py:53-63`, and it works by
substring-matching the prompt. The original version checked for one marker:
`"do not summarize"`. American spelling. The prompt above says `summarise`. The check
therefore never matched.

The consequence: with no API key, the cleaning pass replaced the entire lecture
transcript with a synthetic placeholder built from word frequencies. The knowledge core
was then extracted from *that* placeholder. And because every artifact in the product is
generated from the knowledge core, every quiz, every flashcard, every mock exam was
built on a stub rather than on the source material. Nothing raised. No exception, no
warning, no failed job. The output was structurally valid and looked entirely plausible.
Silent data corruption from a single letter.

The fix is at `backend/llm/offline.py:24-30`:

## The regex table

```python
TRANSCRIPT_NOISE = (
    re.compile(r"\b\d{1,2}:\d{2}(:\d{2})?\b"),
    re.compile(r"\b[A-Z]{2,}:\s*"),
    re.compile(r"\([^)]*\)"),
    re.compile(r"\[[^\]]*\]"),
)
```

`cleaning.py:27-32`. Four patterns, compiled once at import rather than on every call —
`re` does cache internally, but compiling at module level makes the intent explicit and
takes the lookup out of the loop.

Note the name. It says `TRANSCRIPT_NOISE`, and that is now a statement of scope rather
than a description: these four are reachable only from `strip_transcript_noise`.

The first matches timestamps: one or two digits, colon, two digits, optionally another
`:MM`. So `14:32` and `1:14:32` both go. The `\b` anchors stop it eating the middle of a
longer number.

The second matches speaker labels of the shape `SPEAKER:` or `AB:` — two or more capital
letters followed by a colon and any trailing whitespace.

The third and fourth remove parenthesised and bracketed content: `(laughter)`,
`[inaudible]`, `[crosstalk]`. `[^)]*` and `[^\]]*` are negated character classes, which
makes each match stop at the first closing bracket instead of running greedily to the
last one on the line.

**Worth knowing**, and it is the whole reason the file has two cleaners: patterns two,
three and four are blunter than they look, and on anything other than speech they are
destructive.

`\b[A-Z]{2,}:\s*` matches `HTTP: `, `TCP: `, `SQL: `, `API: ` and `NOTE: ` — a document
that writes "HTTP: a stateless protocol" loses the term being defined. `\([^)]*\)`
deletes every parenthesis, so `f(x)` becomes `f`, `O(n log n)` becomes `O`, and
`sum(values)` becomes `sum`. `\[[^\]]*\]` deletes every bracket, so the interval `[0,1]`
and the citation `[Knuth 1998]` both go. And the timestamp pattern eats the ratio `3:14`,
because it cannot tell a ratio from a clock.

On a maths or computer-science PDF — exactly the material this product targets — that is
not degradation, it is removal of the content. And it was happening to every document,
silently, until the split.

Two things are worth saying in the same breath, because they are the reason these rules
still exist rather than being softened. First, they remove genuine transcription noise
that would otherwise poison the core, and on speech there is nothing for them to damage:
a `(` in a transcript was not spoken. Second, a rule that tried to be clever — keep
`f(x)` but drop `(laughs)` — would have to decide what is notation and what is an aside,
and it would be wrong sometimes in both directions. Making the rules exact and then
routing by source type gives a rule that is always right on the input it sees, which is
the better shape. What is left is the routing decision, and that is one set membership
test with an allowlist that fails safe.


`cleaning.py:34-36`. The rest of the transcript-only set.

`FILLERS` is the one that most needs its `\b` word boundaries, and the boundaries are
the reason this is safe. Without them, `er` would match inside "however", "under",
"error" and several thousand other words. With them it only matches the standalone
word. `re.IGNORECASE` catches "Um" at the start of a sentence.

`REPEATED_PERIODS` collapses ellipses and the `...` that transcribers use for trailing
speech into a single full stop.

`WHITESPACE` collapses any run of whitespace — including newlines — to one space. It is
used at `cleaning.py:134`, `:162` and `:177`, all on the transcript side, and its
including newlines is the point there: a transcript has no meaningful layout and
flattening it is correct. It is also the rule that used to destroy the page markers when
documents came through here.

```python
INVISIBLE_CHARACTERS = re.compile("[\x00-\x08\x0b\x0c\x0e-\x1f\x7f\u00ad\u200b\ufeff]")
HORIZONTAL_WHITESPACE = re.compile(r"[^\S\n]+")
LINE_PADDING = re.compile(r" ?\n ?")
BLANK_LINES = re.compile(r"\n{3,}")
SPACE_BEFORE_PUNCTUATION = re.compile(r"[^\S\n]+([.,!?;:])")
```

`cleaning.py:38-42`. The document set, and every one of them is chosen to be unable to
delete a character a person typed.

`INVISIBLE_CHARACTERS` is a single class of things that carry no text at all. The ranges
cover the C0 control characters *except* tab (`\x09`), newline (`\x0a`) and carriage
return (`\x0d`), which are deliberately spared because they are layout. `\x0b` is the
vertical tab and `\x0c` the form feed, which PDF extraction inserts at page boundaries.
`\x7f` is delete. Then three named troublemakers that a PDF or a Word document routinely
carries and that nothing downstream wants: `\u00ad`, the soft hyphen, which a justified
PDF puts inside words and which turns "protocol" into "pro-tocol" once the layout is
gone; `\u200b`, the zero-width space; and `\ufeff`, the byte-order mark, which arrives at
the head of a file written on Windows.

Note that this is the only *deleting* rule on the document path, and every character it
deletes renders as nothing. That is the invariant that makes `clean` safe to hand text
you have not looked at.

`HORIZONTAL_WHITESPACE` is `[^\S\n]+` and that double negative is the crux of the whole
document path. `\S` is non-whitespace, so `[^\S...]` is "whitespace", and `[^\S\n]` is
"whitespace that is not a newline". So it collapses runs of spaces and tabs and leaves
line structure alone. This is the deliberate opposite of `WHITESPACE` above, and the
difference between the two is exactly the difference between the two cleaners.

`LINE_PADDING` removes a single optional space either side of a newline, which is what
is left after the previous rule collapses a run of trailing spaces at the end of a line
down to one.

`BLANK_LINES` caps a run of three or more newlines at two, so a paragraph break survives
and the six blank lines a page break leaves behind do not.

`SPACE_BEFORE_PUNCTUATION` is the one constant both cleaners share — the document path
calls it at `cleaning.py:114` and the transcript path at `:135` — and it is defined here,
in the document group, because the document path is the one with the stricter
requirement. It matches `[^\S\n]+` rather than `\s+`, so it will not pull a full stop at
the start of one line up onto the end of the previous one. The transcript path does not
care, since it has already flattened its newlines by the time it calls this; the document
path would be corrupted by the looser version.

It captures the punctuation mark in a group so the substitution can put it back, the
replacement being `r"\1"`: delete the whitespace, keep the mark. On the transcript side
it is cleanup after the deletions, because removing `(laughter)` from
"and then, (laughter) we saw" leaves a space before the comma. On the document side it
tidies an extraction artefact, because PDF readers frequently emit a space before a full
stop where the original layout had one.

```python
MARKDOWN_MARKS = (
    (re.compile(r"\*\*([^*]+)\*\*"), r"\1"),
    (re.compile(r"\*([^*]+)\*"), r"\1"),
    (re.compile(r"__([^_]+)__"), r"\1"),
    (re.compile(r"`([^`]+)`"), r"\1"),
    (re.compile(r"^#{1,6}\s+", re.MULTILINE), ""),
)
```

`cleaning.py:44-50`. Pairs of pattern and replacement, applied in order.

The ordering is not incidental: `**bold**` must be handled before `*italic*`, because
the single-asterisk pattern would otherwise match the first `*` of a `**` pair and leave
a stray asterisk behind. Each keeps its inner content via the `\1` backreference,
stripping only the marks.

The last one is headings, with `re.MULTILINE` so `^` means "start of any line" rather
than "start of the string", and no replacement at all.

Why this exists: models add Markdown formatting unprompted, even when told to output
plain text. This is the belt-and-braces to the prompt's "Output plain text only". It
matters because the knowledge core is contractually plain text, and
`KnowledgeCoreValidator` at `backend/handlers/ingest_handler.py:57-66` will fail an
ingest outright if markup survives into it.

## `TextCleaner`

```python
class TextCleaner:
    """
    Cleans text with the rules the source it came from can survive.

    Transcribed speech is prose and nothing else, so it can afford the
    destructive rules: parentheses and brackets there hold `(laughs)` and
    `[inaudible]`, line breaks hold nothing, and a model pass is worth its risk
    because transcription really does produce broken grammar.

    A document is not prose alone. Parentheses and brackets carry meaning
    (`f(x)`, `[0,1]`, `O(n log n)`, bracketed citations), a colon follows words

    readers insert are structure the material is navigated by. Documents
    therefore get whitespace normalisation and nothing that can delete a
    character the author typed.

    `clean` is the conservative path and holds the plain name on purpose: a
    caller that does not know which kind of source it is holding must not be

        self._provider = provider or get_provider()
```

`cleaning.py:53-76`. Same injectable-provider constructor as everywhere else, and a
docstring that is now doing most of the explaining.

The last paragraph is the design decision most worth being able to defend, and it is a
naming decision rather than a technical one. There were two ways to name these methods.
`clean_document` and `clean_transcript` would be symmetrical and neither would be the
default. `clean` and `clean_transcript` is what was chosen, and the plain name is on the
*safe* path deliberately.

The argument is about what happens when someone gets it wrong. A caller that reaches for
the obvious name, or a future stage that does not know what kind of text it is holding,
lands on the conservative cleaner and the worst outcome is text that is slightly less
tidy than it could have been. Under the symmetrical naming there is no obvious name, so
the failure mode is a coin flip; under a naming where `clean` did the destructive thing —
which is exactly what the file used to have — the worst outcome is silent destruction of
notation. The destructive rules should have to be asked for by name, because asking for
them by name is a statement that you know what you are holding.

That is a small instance of a general principle worth stating in those terms: when two
operations differ in how bad it is to pick the wrong one, the cheaper-to-get-wrong one
should be the one that is easier to reach.

```python

        risk would buy nothing.
```

`cleaning.py:78-88`. One line of body, and two things about it are worth explaining.

**It is `async def` with nothing to await.** That looks like a mistake and is not. The
signature is the seam: `IngestHandler._clean` awaits whichever of the two cleaners it
picked, so both have to be awaitable or the caller would need to know which one it was
holding — which is exactly the knowledge this design is trying to keep in one place. It
also leaves the door open: if the document path ever does acquire a model pass, no caller
changes. The cost is one coroutine object per ingest. `RecordingCleaner` in
`backend/tests/test_pipeline.py:193-205` is the stub built to that shape, with both
methods `async` and each recording which path the handler chose.

**It runs no model pass at all**, and this is the part to argue rather than assert,
because "you removed the model call" is the obvious thing to be challenged on. Three
reasons, in order of how conclusive they are.

The mechanical one first, because it is decisive on its own. Look at `_repair` further
down: it splits the text into chunks and rejoins them with `" ".join(...)`, then runs
`WHITESPACE.sub(" ", ...)` over the result. Both of those flatten newlines. So even a
model pass that was perfectly faithful — one that returned every chunk byte-identical —
would still deliver the document back as a single line with the `--- Page N ---` markers
buried inside it. The repair machinery is built for text that has no layout, and a
document has layout.

The second is that there is nothing for it to repair. The whole justification for the
model pass is that speech-to-text output has misplaced sentence boundaries, homophone
errors and inconsistent terminology. A PDF has none of those. Its author typed it, a
publisher typeset it, and the words are already the words.

The third is risk. `REPAIR_PROMPT` asks a model to rewrite prose. Handed a page of
mathematics it may well "fix" notation it was never asked to touch, and the offline
provider's passthrough gate — the locale bug above — is a phrase match that could fail
again. Every model call is a chance to change text that did not need changing, and here
the expected benefit is zero, so any risk at all is a bad trade.

The removed `use_model` flag is worth a sentence, because the old version had one. It
existed so tests could run the regex pass without spending tokens. It is gone from
`clean` because there is no model pass to switch off, and it survives on
`clean_transcript` where it still means something.

`and cleaned` short-circuits on empty. If the regexes removed everything — a recording

```python
    @staticmethod
    def strip_document_noise(text: str) -> str:
        """
        Normalise whitespace and drop characters that carry no text at all.

        Everything a reader emitted deliberately survives: notation, brackets,
        punctuation and the `--- Page N ---` and `--- Slide N ---` markers,
        which is why line breaks are preserved rather than collapsed. Only
        extraction artefacts go: form feeds, soft hyphens, zero-width spaces,
        ragged spacing and the run of blank lines a page break leaves behind.
        """
        if not text:
            return ""

        text = INVISIBLE_CHARACTERS.sub("", text)
        text = HORIZONTAL_WHITESPACE.sub(" ", text)
        text = LINE_PADDING.sub("\n", text)
        text = SPACE_BEFORE_PUNCTUATION.sub(r"\1", text)
        return BLANK_LINES.sub("\n\n", text).strip()
```

`cleaning.py:97-115`. The conservative cleaner, and the order of the five substitutions
is the argument.

Invisible characters go first, because a soft hyphen or a zero-width space sitting
between a word and a space would otherwise stop the whitespace rules from seeing an
unbroken run.

`HORIZONTAL_WHITESPACE` then collapses runs of spaces and tabs to one space each,
leaving every newline exactly where it was. This is the single line that separates this
cleaner from the old behaviour: the old one used `WHITESPACE`, which includes `\n`.

`LINE_PADDING` tidies the space that the previous rule left immediately before or after
a newline — a line ending in trailing spaces becomes a line ending in one space, and this
removes it.

`SPACE_BEFORE_PUNCTUATION` then fixes the PDF artefact of a space before a full stop,
and it must come after the two whitespace rules because it matches one run rather than
several separate spaces.

`BLANK_LINES` caps runs of newlines at two, which preserves a paragraph break and removes
the gap a page boundary leaves. It comes last because the earlier rules are what turn
`" \n \n \n "` into `"\n\n\n"` in the first place.

`.strip()` on the way out for the leading and trailing whitespace of the document as a
whole, which none of the five rules removes.

The invariant to state out loud: no rule here can remove a printing character. The only
deletion is `INVISIBLE_CHARACTERS`, and every codepoint in it renders as nothing.

```python
    @staticmethod
    def strip_transcript_noise(text: str) -> str:
        """
        Delete every parenthesised and bracketed span, plus timestamps, shouted
        speaker labels and fillers, then flatten the layout.

        Safe only on transcribed speech. The same four rules that remove
        `(laughs)`, `[inaudible]`, `SPEAKER:` and `12:34` will remove `f(x)`,
        `[0,1]`, `NOTE:` and `3:14`, so a document must never reach them.
        """
        if not text:
            return ""

        for pattern in TRANSCRIPT_NOISE:
            text = pattern.sub("", text)

        text = FILLERS.sub("", text)
        text = WHITESPACE.sub(" ", text)
        text = SPACE_BEFORE_PUNCTUATION.sub(r"\1", text)
        return REPEATED_PERIODS.sub(".", text).strip()
```

`cleaning.py:117-136`. The old `strip_noise`, renamed, with a docstring that now names
the constraint. The rules themselves are unchanged, because they were never wrong for
speech.

Both of these are `staticmethod`s because they touch no instance state, which means
either can be called as `TextCleaner.strip_document_noise(text)` with no provider and no
construction — useful in a test, and useful for any stage that wants the rules without
the model.

The order is: destructive removals first, then repairs of the damage those removals
caused. Removing `(laughter)` creates a double space and possibly a space before a comma,
so `WHITESPACE` and `SPACE_BEFORE_PUNCTUATION` have to come after. Reversing them would
leave the artefacts of the earlier passes in place.

`.strip()` at the end removes leading and trailing whitespace, which `WHITESPACE.sub`
would have turned into single spaces rather than removed.

## `_repair` — concurrency, and the `BaseException` detail


`cleaning.py:138-147`.


`cleaning.py:149-152`. All chunks in flight at once. A 40,000-character transcript is ten
chunks; sequentially that is ten round trips, concurrently it is one round trip's
latency. The actual concurrency ceiling is not here — it is the semaphore inside the
provider, `llm_max_concurrency`, defaulting to 6
(`backend/llm/openrouter.py:182`, `backend/core/config.py:126`), which is what keeps this
from firing fifty simultaneous requests at OpenRouter and getting rate-limited.

`return_exceptions=True` is the key argument. Without it, `gather` propagates the first
exception and the entire cleaning pass fails — meaning one transient 503 on chunk 7 of
10 throws away nine successful repairs and fails the whole ingest. With it, failures come
back as ordinary values in the results list, positionally aligned with the inputs.

```python

            chunk if isinstance(result, BaseException) else result
            for chunk, result in zip(chunks, results)
        ]
```

`cleaning.py:154-157`. `zip` pairs each original chunk with its result, which works
because `gather` guarantees result ordering matches input ordering regardless of
completion order. Where the result is an exception, the *original* chunk text is used.
That is the degradation strategy: a failed repair means that section of the transcript
stays as it was — unrepaired but complete — rather than being lost.

`isinstance(result, BaseException)` and not `isinstance(result, Exception)`. This is a
detail worth being able to explain because it is exactly the sort of thing an interviewer
probes. `asyncio.CancelledError` inherits from `BaseException`, not from `Exception` —
that changed in Python 3.8 precisely so that broad `except Exception` handlers do not
swallow cancellation. If a chunk's task is cancelled — job timeout, worker shutdown —
`gather` with `return_exceptions=True` returns the `CancelledError` object as a value.
Checking only for `Exception` would miss it, the object would fall through to the `else`
branch, and a `CancelledError` instance would be placed into a list that is about to be
`" ".join`ed. Which either raises a `TypeError` or, worse, gets stringified into the
transcript as literal text. `BaseException` catches both.

```python

        if failures:
            logger.warning("%d/%d chunks kept their original text", failures, len(chunks))

        return WHITESPACE.sub(" ", " ".join(repaired)).strip()
```

`cleaning.py:158-162`. Degrading silently is how you end up not knowing your pipeline is

ten is noise, nine in ten is an outage.

The two cleaners are only worth anything if something picks correctly between them, and
that something is one method in the handler:

```python
        Send the text to the only cleaning rules its source can survive.

        The transcript rules delete every parenthesised and bracketed span,
        which is what `(laughs)` and `[inaudible]` deserve and what `f(x)`,
```

## Constants and the extraction prompt

```python
SINGLE_PASS_LIMIT = 24_000
CHUNK_SIZE = 12_000
```

`knowledge.py:16-17`. Characters. Under 24,000 the whole text goes to the model in one
request; over that it is split into 12,000-character chunks.

The reason for a single-pass path at all is quality, not cost. One model call over the
whole document sees every cross-reference — the model can tell that the definition given
at the start is the thing being applied at the end. Chunking destroys that, because each
chunk is extracted in isolation and no chunk knows what the others said. So single pass
is the preferred path and chunking is the fallback.

The reason for the fallback is the opposite failure. Give a model an enormous document
and ask for exhaustive structured extraction, and detail degrades towards the end —
attention thins out, and the output budget (`llm_max_output_tokens`, default 16,384)
is finite regardless of how much input you sent. The docstring at
`knowledge.py:96-97` says exactly this: "a single request over a whole transcript loses
detail towards the end."

24,000 characters is roughly 6,000 tokens, well within `google/gemini-2.5-flash`'s
context window. The limit is not about what fits — it is about where extraction quality
starts to fall off. That is the honest answer if asked how the number was chosen.

## `KnowledgeCore`, field by field

```python

    """
    The structured understanding of one body of source material.

    Every generated artifact reads from this rather than from the raw text,
    which is what keeps a project's quiz, notes and exam consistent.
    """

    title: str
    summary: str
    concepts: List[Concept]
    section_hierarchy: List[Section]
    notes: List[NoteBlock]
    definitions: List[Definition]
    examples: List[Example]
    key_facts: List[KeyFact]
```

`knowledge.py:74-89`. Eight fields. Know what each one is for and which artifact
consumes it.

**`title`** — what the material is about, in the model's words. It is the name of the
artifact in the UI, and it names the project's root node on the canvas.

**`summary`** — the whole document in a paragraph. It is what every generator reads
first for orientation, and it is the field a chained non-core artifact borrows when it
has to be wrapped as a synthetic core (`backend/handlers/sources.py:193-200`).

**`concepts`** — the ideas, each with a description and an importance score. This is the
field that lets generation be *selective*: a cheat sheet takes the top few by score, a
mind map uses them as branches, a study guide turns them into objectives. Without the
score every generator would have to decide importance itself, and they would disagree.

**`section_hierarchy`** — the logical structure of the material, two levels. This is what
slide generation follows so the deck runs in the same order as the lecture, and what
gives a study guide its shape.

**`notes`** — the long-form content, grouped by heading. Deliberately the fattest field,
per "prefer detail in the notes over brevity". The notes artifact is largely this, and
everything else draws detail from it.

**`definitions`** — terminology with context. The direct source of definition-style
flashcards and of "define X" exam questions.

**`examples`** — the concrete illustrations, each tied to what it illustrates. These are
what make generated explanations feel like they came from the lecture rather than from
a textbook, and they are the source of applied problems.

**`key_facts`** — atomic checkable statements with categories. The direct source of quiz
questions, because an atomic objective statement is exactly the shape a question needs.

Notice that every collection is `List[...]` with no default. Pydantic therefore requires
all eight fields to be present, and `strict_schema` marks every one `required` in the
JSON Schema sent to the model (`backend/llm/schema.py:40`). The model cannot omit a
field; it can only send an empty list. That distinction matters for the validator, and
it is where the next piece of history lives.

### The validator that was too strict

The knowledge core validator once required every collection to be non-empty. That
sounds reasonable and was wrong.

A short recording — a ten-minute tutorial, a lecture that was pure theory — genuinely
contains no worked examples. The model correctly returned `examples: []`. The validator
saw an empty list, rejected the core, and failed the ingest. A complete and perfectly
usable extraction was thrown away, and the user was told their file could not be
processed, because the material happened not to include a metaphor.

The current version is at `backend/handlers/ingest_handler.py:30-55`:

```python
class KnowledgeCoreValidator:
```

```python

            seen: set = set()
            result = []
            for item in items:
                identity = str(key(item)).strip().lower()
                if identity and identity not in seen:
                    seen.add(identity)
                    result.append(item)
            return result
```

`knowledge.py:143-151`. A closure taking a key function, so one implementation serves all
six collections.

It preserves order — first occurrence wins, later duplicates are dropped — rather than
using a set, because order carries meaning: chunk 1's concepts come before chunk 2's, so
the merged core still roughly follows the material. `.strip().lower()` normalises the key
so "Consensus" and "consensus " are the same thing. `if identity` drops items whose key
is empty, since an empty key cannot be meaningfully de-duplicated and an item with a
blank name is not useful anyway.

Note it de-duplicates on the key but keeps the *whole first item*. So the first
occurrence's description and importance score win, and the second occurrence's are
discarded entirely.

its `name`, a section its `title`, a note block its `heading`, a definition its `term`,
an example its `description`, a fact its `fact`. Those are the fields that actually
identify the item, which is why they are the keys.

`title=cores[0].title` takes the first chunk's title for the whole document. That is a
defensible heuristic — a lecture usually announces its subject at the start — and it is
also a real limitation. **Worth knowing:** the document is named after its opening
12,000 characters, so a lecture with a long administrative preamble gets a core titled
after the preamble. Asking the model to title the merged summary would be better and
would cost one extra call.

The summary concatenation truncates at 4,000 characters with a bare slice, so it can cut
mid-word. It is a hard bound on a field that is otherwise unbounded in the number of
chunks, which is the purpose; it just is not a graceful one.

**Worth knowing**, and the deeper limitation: de-duplication is exact string matching
after lowercasing. "Raft consensus" and "The Raft consensus algorithm" are different
keys and both survive into the merged core, so the same idea can appear twice under two
names. Semantic de-duplication would need embeddings or another model call. Exact
matching catches the common case — the same term extracted identically from two adjacent
chunks — cheaply and deterministically, and the merged core is a little redundant rather
than wrong. That is the trade, stated plainly.

# 6. The design claim, and the limitation

## Why artifacts are generated from the core rather than from the transcript

This is the thing to be able to defend without hesitating, because it is the reason the
project is shaped the way it is.

The naive design is: keep the transcript, and for each artifact send the transcript plus
a different prompt. Quiz prompt, flashcard prompt, slides prompt. It works, and it
produces artifacts that disagree with each other.

They disagree because each generation is an independent act of interpretation. The
quiz generator reads 40,000 words and decides what matters. The flashcard generator
reads the same 40,000 words and decides something slightly different. The slide
generator picks a third structure. Nothing forces them to agree, and at temperature
above zero nothing even forces one generator to agree with itself between two runs. So
the user gets a quiz about topics their notes never cover, flashcards that define a term
the slides use differently, and a mock exam whose sections do not match their study
guide. Every one of those artifacts is individually reasonable and the set is
incoherent.

BeePrepared does the interpretation exactly once. Extraction is the only stage that
reads the source material and forms a view of what it says. That view is the
`KnowledgeCore`, and it is committed as an artifact in the database. Every generator
then reads the core and nothing else — you can see it concretely at
`backend/services/generators.py:232`:

```python
        context = core.model_dump_json()
```

The core is serialised to JSON and passed as `context` to `complete_as`. The generator
never sees the transcript. It does not have access to it. `SourceResolver.to_core` at
`backend/handlers/sources.py:152-172` enforces this at the boundary: whatever artifact
you point a generation job at, it is reduced to a `KnowledgeCore` before any generator
runs, and if no core can be resolved the job fails rather than falling back to raw text.

Four consequences, and these are the answer to "why is this better":

**Consistency by construction.** The quiz and the flashcards test the same `key_facts`
because there is only one list of key facts. They are not consistent because a prompt
asked them to be; they are consistent because they are functions of the same input.

**Cost and latency.** The expensive pass — reading the whole lecture — happens once at
ingest. Generating the eighth artifact costs a request over a few thousand characters of
structured JSON, not another pass over 40,000 words of transcript. Eight artifacts from
one lecture is one big call plus eight small ones, rather than eight big ones.

**Structure the model can use.** A generator asking "what are the most important
concepts" does not have to infer them — it reads `concepts` and sorts by
`importance_score`. The hard problem was solved at extraction time and the answer was
written down.

**One place to be wrong, and one place to fix it.** If the core misses a topic, every
artifact misses it — which sounds like a weakness and is actually the strength. The
failure is visible, attributable to one stage, and fixed by improving one prompt. In the
transcript-per-artifact design the same problem shows up as eight artifacts each wrong in
a different way for reasons you cannot isolate.

The cost, stated honestly: extraction is a lossy compression, and anything it drops is
unrecoverable. That is why `EXTRACTION_PROMPT` says "Be exhaustive" and "prefer detail
in the notes over brevity", why the schema requires all eight fields, and why the
validator rejects a core that has no concepts or no key facts. The whole product rests on
that one call being good.

## Why there is no vector store

Expect to be asked "where's your RAG?" — and the answer is that it would make this
worse, not better.

The reason retrieval-augmented generation exists is that the corpus does not fit in the
context window, so you embed it, chunk it, and retrieve the top-k chunks nearest the
query. One lecture is not that problem. An hour of speech is roughly 8,000 to 10,000
words — well inside `google/gemini-2.5-flash`'s context window, and the whole document
is passed in one call whenever it is under 24,000 characters.

More to the point, top-k retrieval is a worse summary than the knowledge core for this
job. Retrieval gives you the passages nearest to a query, which is right when you have a
specific question. Generating a study guide is not a specific question — it is "give me
everything, organised". Top-k over an hour of lecture would return five disconnected
paragraphs and lose the structure entirely, which is precisely the thing
`section_hierarchy` exists to preserve. The knowledge core is a *complete* structured
representation, not a sample of the nearest chunks.

There is also a cost argument. A vector store is an embedding model, an index, a similarity
search and a chunking strategy, all of which have to be operated and tuned. For a corpus
that fits in the context window, that is infrastructure bought for nothing.

Where it would start to be right, and say this so the limitation is yours rather than
theirs: as soon as a project spans a whole semester — thirty lectures, a textbook, a
problem set archive — the corpus stops fitting and selecting the relevant material
becomes a real problem. At that point the honest design is retrieval *over knowledge
cores*, one per source, rather than over raw chunks. The cores are already structured,
already de-duplicated, and already the right granularity to embed. The architecture does
not have to change to get there; it has to grow a selection step in front of
`SourceResolver`.
